# KI-Stack RAG 0.4.0

Development ingestion module for OpenWebUI 0.11.0. Nomic is the only embedding model. Document and query prefixes are separate. Sources are explicit, hash-controlled and removable by stable `source_id`.

`Config/sources.json` is the explicit source allow-list. Audit, DryRun and Status never mutate the target. Execute creates or reuses one managed Knowledge collection, uploads deterministic local chunks with the complete metadata contract, performs SHA256 delta replacement and removes deleted sources. Tokens are accepted only as `SecureString` and are never stored.

OpenWebUI endpoint contracts are pinned to 0.11.0. Add/Replace/Remove (plus Skip for already-current sources) have passed real target-system validation. Remote Rollback of all three (Add, Replace, Remove) has passed real target-system validation as well, each including idempotency on a repeated call: verified against a live OpenWebUI 0.11.0 instance with before/after evidence (remote file genuinely deleted, not merely detached; restored content byte-verified against the pre-mutation original; local state consistent). Rollback is additionally covered by an extensive mocked regression suite, including explicit partial-failure-then-retry coverage for the Replace/Remove restore path (a real defect was found and fixed there: a retry could re-issue a remove call against remote content an earlier partial attempt had already deleted; the removal is now treated as already-satisfied, matching the real server's behavior, instead of failing the retry).

OpenWebUI 0.11.0 has no collection- or knowledge-scoped embedding contract at all: `RAG_EMBEDDING_ENGINE`/`RAG_EMBEDDING_MODEL` are a single, application-wide setting changed via `POST /api/v1/retrieval/embedding/update`, and `RAG_EMBEDDING_CONTENT_PREFIX`/`RAG_EMBEDDING_QUERY_PREFIX` are fixed at OpenWebUI process startup from environment variables, with no runtime API to change them at all. This is source-confirmed against the actually installed `open_webui-0.11.0` package (`routers/retrieval.py`, `models/knowledge.py`, `config.py`), not inferred from the UI, and re-confirmed against the currently installed `open_webui-0.11.1` package during the 2.12.0 cycle (same env vars, same call sites, still module-level constants read once at import time -- `config.py`, `routers/knowledge.py`, `routers/retrieval.py`). KI-Stack RAG treats this as a hard platform boundary, not a defect to route around: every mutation of the global embedding config is idempotent (skipped once the target is already active), always preceded by a full non-sensitive backup, and only ever auto-restored on Execute failure or a successful Rollback when that backup provably held no omitted credential value. When a real credential was present beforehand, the config is deliberately left at RAG's own working state instead of a broken partial restore, and the result reports `EmbeddingRestoreRequiresManualAction` naming the previous provider/engine/model -- never a secret value.

## Prefix contract: how `search_document:`/`search_query:` actually reach OpenWebUI

`rag.config.json`'s `documentPrefix`/`queryPrefix` are the single source of truth. The Complete Installer's `Install-KICompleteRAGModule` reads them at deployment time and writes `modules/rag/OpenWebUI-RAG.env.cmd` (`set RAG_EMBEDDING_CONTENT_PREFIX=...` / `set RAG_EMBEDDING_QUERY_PREFIX=...`), then patches `modules/integration/Start-KIStack-OpenWebUI-WithSearch.cmd` to `call` that file before OpenWebUI starts -- OpenWebUI's own native environment-variable mechanism, not a KI-Stack-side re-implementation, and not a second, competing prefix mechanism. Prefixing happens exactly once, entirely inside OpenWebUI's own embedding call sites; RAG never prepends a prefix to chunk content itself, so a prefix can never leak into a chunk's stored/visible text and can never be doubled by a re-import.

**Known-and-fixed regression (2.12.0):** Integration owns and unconditionally regenerates `Start-KIStack-OpenWebUI-WithSearch.cmd` on every Install/Upgrade/Repair pass. Before this fix, that regeneration silently erased RAG's `call "...\OpenWebUI-RAG.env.cmd"` line whenever Integration reconciled without RAG also running in the same transaction -- confirmed as a live regression on the real target (the RAG env file predated the starter's last rewrite by a full day). `Get-KIIntegrationOpenWebUIWithSearchStarterContent` (`KIModuleIntegration.psm1`) now preserves an already-applied RAG env-call line across every regeneration; see `Test-KIStackIntegrationRAGStarterPreservation.ps1`.

## Metadata contract

Every chunk's header carries the full `metadataFields` list from `rag.config.json`, including the two fields a retrieval answer must minimally be traceable through: `source_file` (the source-relative path; identical to `relative_path`, kept alongside it for backward compatibility) and `chunk_index` (zero-based, contiguous per source file). Combined with `source_id`, `source_file` + `source_id` uniquely identify the originating document.

## Global vs. project-scoped knowledge

One `rag.config.json`/`sources.json` pair is one scope, mapped to exactly one OpenWebUI Knowledge collection (`Get-RAGKnowledgeName`): the `global` scope (the default, `Config/rag.config.json`) uses `knowledgeName` unchanged; any other `project` value gets its own collection named `"<knowledgeName> -- <project>"`. Every enabled source in a scope's `sources.json` must declare that exact same `project` (`Test-RAGSourcesMatchConfiguredProject`), so a source can never silently land in the wrong scope's collection. This is OpenWebUI's own native collection-isolation mechanism -- a project's documents only ever surface when that project's collection is explicitly attached to a chat/model, never in an unrelated global answer -- not a bespoke tenancy layer.

Use `New-KIStackRAGProjectScope.ps1 -ProjectName <name>` to create a new, fully isolated project scope (its own `stateRoot`, `sourceRoot`, `sources.json`, and derived `knowledgeName`) from the global configuration; it refuses to overwrite an already-existing scope unless `-Force` is passed, and refuses the reserved name `global`. Operate a project scope with the same, unmodified entry point used for the global one:

```
Invoke-KIStackRAG.ps1 -Mode Execute -ConfigPath Config\rag.config.<name>.json -SourcesPath Config\sources.<name>.json -ApiToken $token
```

See `Test-KIStackRAGScopeSeparation.ps1` for the full contract (naming, source/scope-match validation, a real HTTP round trip proving two scopes resolve to two distinct, independently reused Knowledge collections, and the scope-creator script's own idempotent-refusal behavior).

## Automation

`Invoke-KIStackRAG.ps1` is the schedulable entry point for every mode (`Audit`, `DryRun`, `Execute`, `Status`, `Rollback`); a script-terminating error propagates as a non-zero process exit code, so it composes into any external scheduler without a wrapper. `Execute` is safely re-runnable: a partial failure leaves already-committed entries in `state.json` untouched (a retry only reprocesses what did not finish, never re-uploads what did -- proven by `Test-KIStackRAGStatePersistence.ps1`'s Scenarios 1/3/7/18), and one source's failure does not roll back or block any other source already committed in the same run.
