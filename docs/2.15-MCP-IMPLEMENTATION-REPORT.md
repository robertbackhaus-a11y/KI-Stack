# KI-Stack 2.15 — MCP Implementation Report

Phase 7 productization report. Covers the work performed to turn the proven MCP spike/migration
(Phases 0–6) into a maintained, isolated, documented KI-Stack component, per the explicit constraints:
no new architecture, no fork of Open Terminal/FastMCP, no new Windows-control capabilities, no agent
memory, no GUI automation, no hard cutover of the legacy path, no commits/tags/pushes, no release
creation. This document is the release-gate evidence record required before any future release
decision — it is not itself a release, and produces none.

## Executive Summary

2.15 replaces the bespoke Open-Terminal-OpenAPI integration with native MCP as the **default**
terminal/host-control path for Open WebUI, for all four real, terminal-capable production profiles.
The migration itself (Phases 0–6) was already complete and independently verified before this phase
began. Phase 7's job was to productize that proven state: pin the runtime's external dependency to
the one version ever actually exercised, make the one real bug found during migration
(Open-Terminal registration credential drift) permanently repairable instead of a one-off manual fix,
close a real gap in Agent Pack's own reconcile logic that would otherwise have silently reverted the
migration on a routine future run, add a read-only LM Studio baseline check, mark the legacy path as
deprecated-as-default without removing it, and re-verify component isolation including the first real
exercise of the new version pin. A repository regression run also surfaced and fully resolved two
real, pre-existing issues unrelated to MCP itself: an ungit-tracked build input, and a local
(never-committed) plaintext credential-hygiene finding — both closed out with user-directed remediation
and re-verified.

A follow-up task this session re-investigated the Gates 5–7 blocker from first principles rather than
reusing prior-phase conclusions, and found it was actually two separate things: (a) no built package
existed to run Gates 5/6 from at all — fixed by building one for real via the existing, unmodified
package builder; Gates 5 and 6 now **PASS** with fresh evidence against the real target; and (b) Gate 7
(Execute) failed cleanly at a genuine elevation check from within this session's own account (confirmed
precisely: this environment's Windows account is not an Administrators-group member at all). A second
follow-up task then found and fixed a real, distinct bug this uncovered: a genuine, successful,
elevated Execute of `cutover-runtime` (run by the user from outside this session) was still reported
non-compliant by every subsequent Audit, because `Get-KICompleteInstalledVersion`'s frozen
acceptance-map fallback always took priority over the component's own real, live, per-target marker —
fixed with a narrow, `cutover-runtime`-only change. A subsequent full, genuine Execute run (again from
the user's own elevated context) then completed real, top-level `status:"Completed"`, all 16 components
`exitCode:0`, `cutover-runtime` and `mcp-runtime` both correctly `compliant:true` — independently
verified by this session directly against the real target's own transaction record, not taken on faith.
All eight `docs/RELEASE-PROCESS.md` gates now carry real evidence. This means **READY FOR RELEASE** —
see Release Gate Status, Release Gate Investigation, and Post-Execute Cutover-Runtime Compliance Fix
below for the full, gate-by-gate accounting.

## MCP Runtime

`tools/mcp-runtime/current/` is a self-contained ("isolation A") Complete Installer component, built
in Phases 1–2 and hardened in Phase 5, confirmed present and unchanged in structure at this phase's
own inventory check. It runs `open-terminal mcp --transport streamable-http` via
`uv run --with open-terminal[mcp]==0.11.34`, bound to `127.0.0.1:8021`, exposing 12 real MCP tools
(`run_command`, `get_process_status`, `kill_process`, `send_process_input`, `list_processes`,
`read_file`, `write_file`, `replace_file_content`, `list_files`, `glob_search`, `grep_search`,
`display_file` — confirmed via a real `POST /api/v1/configs/tool_servers/verify` call, not assumed).

**This phase's change:** `Config/mcp-runtime.config.json`'s `packageSpec` was pinned from an
unversioned `"open-terminal[mcp]"` to `"open-terminal[mcp]==0.11.34"` — the single version resolved
by `uv` in every test across Phases 0–6, confirmed via `uv` cache inspection. The pin was then
exercised for real for the first time in this phase: a controlled Stop/Start of the production
instance, followed by direct confirmation that the running process's own command line carries
`open-terminal[mcp]==0.11.34` and that `open_terminal-0.11.34.dist-info` genuinely exists in the `uv`
cache — the pin resolves as intended, not merely as configured.

## Auth Handling

Two distinct credential surfaces exist and were both addressed this phase:

1. **Open Terminal's own registration key** (`terminal_server.connections`, a legacy-path concern):
   a real drift bug was found during Phase 6 testing (Open Terminal's DPAPI credential regenerated
   out-of-band; the registered key in Open WebUI went stale, causing `HTTP 401` on every legacy tool
   call while the component itself stayed healthy). Fixed once, manually, in Phase 6; made permanently
   repairable this phase via a new, narrow, idempotent action:
   `Invoke-KIStackOpenTerminal.ps1 -Action SyncRegistrationCredential` — updates only the `key` field
   of the matching registration (matched by port, not an exact host-string, after a real matching bug
   was found and fixed during this phase's own testing), never re-registers, never logs or returns the
   plaintext key.
2. **The shared OpenWebUI admin bootstrap credential** (`Lifecycle/KIStackOpenWebUICredential.psm1`,
   used by MCP Runtime, Open Terminal, and the Complete Installer's own bootstrap path): found, during
   this phase's own regression run, to be exposed in plaintext in a local, never-git-tracked Claude
   Code permission cache (`.claude/settings.local.json`) — the same key as the one from the original
   latency-diagnostics session, still the currently active production key. Per explicit user
   direction: rotated via the already-existing `Initialize-KIStackOpenWebUICredential.ps1 -Rotate`
   path (run by the user themselves in a real interactive terminal — the admin password never passed
   through this session), the 6 affected plaintext entries removed from the local settings file, and
   the rotation's success and continuity confirmed functionally (new key `status:Valid`, role `admin`,
   production automation continuing to work unchanged). See Security Notes for the full account.

## Agent Pack Integration

**The most significant finding of this phase.** `OpenWebUIAgentPack.psm1`'s reconcile logic
previously regenerated a profile's `meta.toolIds` entirely from `$ExtensionToolIds` plus the profile's
own JSON definition on every Upgrade/Repair — with no awareness at all of the
`server:mcp:ki-stack-mcp-runtime` reference appended outside that mechanism during Phase 6. A future,
entirely routine Agent Pack run on `ki-stack-it-technik` or `ki-stack-allgemein` would have silently
reverted the MCP migration, without any error or warning. Fixed by adding a dedicated,
`mcpBinding`-gated `$mcpServerToolIds` list to `New-AgentPackModelForm`'s generated `toolIds` (additive,
not replacing), plus the matching extension to the live-target validation logic
(`$expectedMcpToolIds`, combined into `$expectedToolIds`). `ki-stack-research.json` was given an
explicit `"mcpBinding": false`. Verified via a real `Test-OpenWebUIAgentPack` run against the
production instance: PASS, byte-exact reproduction of the live state, zero drift.

## Release Gate Investigation (this session's follow-up task)

A dedicated, fresh investigation was performed into the Gate 5–7 blocker, per explicit instruction to
reproduce current state rather than reuse prior-phase conclusions, with two genuinely distinct root
causes found and separated:

**Root cause A — path/context problem (Gates 5 and 6), found and fixed this session:**
`Invoke-KIStackCompleteInstaller.ps1`'s own `Get-KICompletePackageRoot` requires both a `MANIFEST.json`
and a `Payload/` directory at (or up to two levels of single-child nesting below) its own location.
`tools/complete-installer/current/Payload/` does not exist in a plain dev-tree checkout by design — it
is a build output populated only by `New-KIStackCompleteInstallerArchive.ps1` (confirmed: never
git-tracked, no `.gitignore` entry needed since it never existed there; a real ad-hoc copy of it,
placed manually into the dev tree in Phase 5 purely as narrow seeded-test input, was correctly removed
during that phase's own cleanup — this was never meant to be how the installer is actually run). The
Complete Installer's own entry point is designed to be run from an **extracted, built package**, not
directly from its own source tree. Minimal fix applied: built a real, current package via the existing,
unmodified `New-KIStackCompleteInstallerArchive.ps1` builder into `dist/complete-installer-phase7-gates/`
