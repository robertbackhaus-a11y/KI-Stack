## 1. Motivation

Open WebUI 0.11.3 bringt einen MCP-Client bereits mit (`connect_mcp_server`, `mcp_clients` in `open_webui/utils/middleware.py`), der im KI-Stack aktuell an keiner Stelle genutzt wird. Gleichzeitig existieren heute zwei getrennte, KI-Stack-eigene Integrationswege für lokale Fähigkeiten:

- individuelle OpenWebUI-Tool-Klassen (`tools/openwebui-visual-pack/current/Tool/*.py`)
- Open Terminal als eigener OpenAPI-Tool-Server mit bespoke Anbindung in Open WebUI (`terminal_event_handler`, `build_terminal_file_tool_result`, `terminal_id` in `open_webui/utils/middleware.py`)

Jede neue Fähigkeit bedeutet bisher: neuer, KI-Stack-spezifischer Code, der dauerhaft gepflegt werden muss. Ziel von 2.15: **MCP wird die verbindliche Standardschnittstelle für lokale Agenten-, Shell- und Host-Control-Fähigkeiten.** KI-Stack-spezifische Fachfunktionen wie Bild-/Videogenerierung bleiben dort bei nativen Tools/APIs, wo dies technisch sinnvoller ist — 2.15 migriert ausdrücklich nicht die Visual-Tools, sondern ausschließlich den bespoke Terminal-Pfad.

---

## 2. Zielarchitektur (nach vollständiger Migration, nicht 2.15-Endzustand)

**Verifiziert (2026-09-04):** Open Terminal unterstützt bereits nativ einen MCP-Servermodus — `open-terminal mcp --transport streamable-http --host 127.0.0.1 --port ...` (per `--help` am installierten Paket bestätigt) —, und Open WebUI unterstützt diesen Transport nativ. Ein eigener Protokoll-Proxy ist damit unnötig; die Zielarchitektur ist direkt:

```
OpenWebUI Agent
       │
       │ MCP / Streamable HTTP
       ▼
Open Terminal im MCP-Modus
       │
       ├── PowerShell / Shell
       ├── Dateien
       └── Prozesse
```

Open Terminal als eigenständiger OpenWebUI-**OpenAPI**-Tool-Server und der bespoke Terminal-Codepfad in Open WebUI **entfallen**, sobald funktionale Parität bewiesen ist (siehe Abschnitt 6.3/6.4). Der Open-Terminal-*Dienst* selbst bleibt bestehen — er wechselt nur seinen Anbindungsmodus von OpenAPI-Tool auf natives MCP. Kein dauerhafter Parallelbetrieb zweier Tool-Systeme.

## 4. Baustein: LM-Studio Runtime Baseline

Aus der Latenzdiagnose vom 2026-09-04 (vollständige Zeitstempel-Beweise in `REPORT.md`):

- **Zielwert:** `Max Concurrent Predictions = 3` für das aktuelle 27B-Modell.
- **Nachgewiesen:** bei Wert `1` wartete ein nachfolgender Request bis zu 160s auf seinen ersten Content-Chunk, weil LM Studio Requests an ein Modell seriell verarbeitet. Bei `3`: First-Chunk-Delay sank auf ~1,3s, Durchsatz bei 3 parallelen Requests ~98 Tok/s kombiniert (33 Tok/s je Request), VRAM stabil bei ~28,8/32,6 GB (~3,8 GB Reserve), keine Queue-Blockade mehr.

Bleibt offen als "beobachten, nicht abschließend erklärt" — kein Blocker für 2.15, aber im Known-open-items-Eintrag entsprechend präzisieren statt als vollständig gelöst zu markieren.
- **Acceptance-Verhalten:** Installer/Acceptance prüft den konfigurierten Wert und warnt bei `1`, überschreibt ihn aber nicht ungefragt (LM-Studio-Settings-Änderungen bleiben nutzergesteuert).

## 5. Baustein: MCP Runtime als Plattformkomponente

Neue, eigenständig versionierte Komponente nach bestehendem Muster (vgl. `tools/open-terminal/current/`):

```
tools/
└── mcp-runtime/
    └── current/
```

Rolle: **KI-Stack-Lifecycle-/Integrationskomponente, kein eigener MCP-Proxy.** Sie startet/stoppt Open Terminal im nativen MCP-Modus, registriert ihn bei Open WebUI, prüft Dependencies (siehe 6.2), pinnt Versionen und übernimmt Healthcheck/Recovery/Acceptance:

```
mcp-runtime
├── Installation/Dependency-Prüfung
├── Start/Stop
├── OpenWebUI-Registrierung
├── Healthcheck
├── Versionspinning
├── Recovery
└── Acceptance
```

**Credential-Handling:** native OpenWebUI-MCP-Credential-Mechanismen werden bevorzugt — Open WebUI behandelt MCP-Verbindungen administrativ und bringt eigenes Connection-/Auth-Handling auf Integrationsebene mit. DPAPI wird nur für KI-Stack-eigene Secrets verwendet, die nicht bereits sicher durch Open WebUI verwaltet werden. Kein zweiter Credential-Store für denselben MCP-Server.

## 6. Baustein: Open-Terminal-Migration

### 6.1 Architekturentscheidung: native Anbindung, kein Fork, kein Proxy

Die eigentliche Terminal-Ausführungslogik liegt im per `uv` installierten, externen PyPI-Paket `open-terminal` — `OpenTerminal.psm1` im Repo verwaltet nur dessen Lifecycle. Da `open-terminal` selbst bereits einen nativen MCP-Servermodus mitbringt (`open-terminal mcp --transport streamable-http ...`, verifiziert), entfällt jede Notwendigkeit für einen KI-Stack-eigenen Übersetzungslayer. „Bestehende Engine wiederverwenden" bedeutet konkret: Open Terminal wird im MCP-Modus statt im bisherigen OpenAPI-Modus gestartet und direkt bei Open WebUI als MCP-Server registriert. Kein Fork, kein Vendoring, kein Proxy.

### 6.2 Vor Umsetzungsbeginn zu prüfen

1. **Welche im KI-Stack installierte Open-Terminal-Version unterstützt MCP, und welche Version wird für 2.15 gepinnt?** Konkret bereits festgestellt: die aktuell installierte Instanz meldet beim Start im MCP-Modus `Missing MCP dependencies. Install with: pip install open-terminal[mcp]` — das `[mcp]`-Extra ist heute **nicht** installiert und muss Teil der Versions-/Dependency-Pinning-Arbeit von `mcp-runtime` werden (nicht automatisch vorausgesetzt).
2. **Unterstützt Open WebUIs eigener MCP-Client (`connect_mcp_server`, `open_webui/utils/middleware.py`, Version 0.11.3) Streaming/langlebige Sessions über den `streamable-http`-Transport in vollem Umfang, oder nur synchrone Tool-Aufrufe?** Entscheidet, ob Session-/Streaming-Parität (siehe Matrix) architektonisch überhaupt erreichbar ist.
3. **Denylist-Disziplin für das neue Agentenprofil:** analog zu `ki-stack-research` (das explizit `terminal: false` und keine Extension Tools über die eigene Wissensbasis/Websuche hinaus bindet) soll das neue Profil ausschließlich an diesen einen MCP-Server gebunden werden — keine zusätzlichen Fähigkeiten "nebenbei" freigeschaltet.

### 6.3 Funktionsparität-Matrix

Vor Entfernen des bespoke Terminal-Pfads (`terminal_event_handler`, `build_terminal_file_tool_result`, `terminal_id`) müssen alle Gate-Zeilen grün sein.

**Ergebnisse aus dem Phase-0-Spike (2026-09-05), zweistufig getestet — Stufe 1: Open Terminal MCP direkt (ohne Open WebUI); Stufe 2: Open WebUI → generischer `tool_server.connections` (type=mcp) → Open Terminal:**

| Fähigkeit | DIRECT MCP (Stufe 1) | OPENWEBUI MCP (Stufe 2) | Bewertung | Klassifikation |
|---|---|---|---|---|
| PowerShell-Ausführung | PASS | PASS | Trägt korrekt | MUST |
| Dateien lesen/schreiben | PASS | PASS | Trägt korrekt | MUST |
| Prozesssteuerung (`run_command`, `kill_process`) | PASS | PASS | Trägt korrekt | MUST |
| Exitcodes | PASS | PASS | Trägt korrekt | MUST |
| Timeout / bounded wait (`wait`-Parameter) | PASS | PASS | Trägt korrekt | MUST |
| In-Flight-Cancel (`kill_process`) | PASS (0,11s / 0,1s, sauber) | PASS (0,1s, sauber) | Trägt korrekt — sogar eine echte Fähigkeit, die der alte bespoke Pfad laut Code-Analyse (`terminal_event_handler` ist reines UI-Refresh, kein Cancel) gar nicht bietet | MUST (jetzt bewiesen statt nur SHOULD/Capability-Check) |
| Parallele unabhängige Aufrufe | PASS (zwei `run_command` liefen nachweislich gleichzeitig) | Mehrfacher sequenzieller Tool-Gebrauch in einer Session bewiesen (write→read→run→kill); echte gleichzeitige Sessions nicht gesondert erneut getestet, aber Mechanismus (unabhängige `client.call_tool`-Aufrufe) identisch zu Stufe 1 | Trägt korrekt (aus Stufe 1 übertragbar) | MUST |
| Transport: `X-Session-Id`-Header-Weiterleitung (`get_http_headers()`) | PASS (sequenziell + parallel, keine Vermischung) | nicht separat erneut isoliert getestet in Stufe 2 (architektonischer Nachweis bereits in Stufe 1 erbracht) | — | Architekturnachweis, kein Release-Gate |
| Working-Directory-Persistenz über mehrere Befehle einer Session | NOT SUPPORTED | NOT SUPPORTED | N/A / parity preserved — verifiziert: `POST /files/cwd`, die einzige Stelle die `_set_session_cwd()` schreibt, ist `include_in_schema=False`, taucht in keiner der beiden Tool-Listen auf. Bestehende Baseline-Limitierung in Open Terminal selbst, keine MCP-Regression. | N/A |

**SHOULD-Kriterien — nicht Teil dieses Spikes, weiterhin offen:**

| Fähigkeit | Status |
|---|---|
| Streaming stdout/stderr (inkrementell, nicht nur Poll-basiert über `get_process_status`) | nicht getestet |
| Terminal-Dateien im Chat (`display_file`-Integration in die UI) | nicht getestet |
| Status-Events (`terminal:*`-Events analog zum bespoke Pfad) | nicht getestet — MCP hat dafür keinen äquivalenten Mechanismus, da `terminal_event_handler` UI-spezifisch an den alten Pfad gebunden ist; müsste in Phase 1 als separates UI-Anliegen behandelt werden |
| Umgebungsvariablen-Persistenz innerhalb einer Session | entfällt (siehe CWD-Zeile — auch im Original nicht unterstützt) |

**Kritischer Nebenfund aus Stufe 2 (kein MCP-Bug):** Der Async-Chat-Completion-Pfad (`session_id`+`chat_id`) verarbeitet Tool-Calls **nur korrekt, wenn der Request `"stream": true` setzt**. Mit `"stream": false` liefert `chat_completion_handler` ein bereits fertiges `dict` mit `tool_calls`, aber `process_chat_response` durchläuft die Tool-Ausführungsschleife (die MCP wie auch vermutlich den Legacy-Pfad gleichermaßen betrifft) dann nicht — die Nachricht bleibt dauerhaft bei `done:false` hängen, ohne Fehler, ohne Exception. Das ist **keine MCP-spezifische Einschränkung** (isoliert bewiesen über Marker MCP-M bis MCP-R: Verbindung und Tool-Discovery liefen bei `stream:false` normal, nur die Tool-Ausführung wurde nie erreicht) und **kein reales Problem für den produktiven Betrieb**, da der echte Browser-Client immer `stream:true` sendet. Wird hier dokumentiert, damit zukünftige manuelle API-Tests nicht erneut denselben (Nicht-)Befund für einen Bug halten.

**Gesamtergebnis Phase-0-Spike: PASS.** Alle als MUST klassifizierten Zeilen sind grün (Stufe 1 UND Stufe 2). Die verbleibenden SHOULD-Zeilen sind explizit ungetestet, nicht fehlgeschlagen — sie blockieren laut Abschnitt 6.4 den Cutover nicht, sollten aber vor einem produktiven 2.15-Release noch geprüft werden, insbesondere die Status-Events-Frage (UI-Anliegen, kein reines Transportproblem).

### 6.4 Migrationspfad (kein Big Bang, kein Dauerbetrieb zweier Systeme)

- **Entwicklung:** Open Terminal im MCP-Modus wird parallel zum bestehenden OpenAPI-Pfad betrieben. Legacy-Pfad bleibt aktiver Fallback.
- **Release-Gate 2.15:** Alle als **MUST** klassifizierten Zeilen der Parität-Matrix müssen grün sein. **Falls ein MUST-Kriterium nicht erfüllt ist: kein MCP-Cutover in 2.15** — die Matrix ist Gate, nicht Orientierung; ein nicht vollständig grüner Stand darf nicht trotzdem als Default freigegeben werden.
- **2.15 Final (nur wenn das Gate besteht):** MCP ist Default. Legacy-Pfad darf für ein definiertes Deprecation-Fenster deaktiviert vorhanden bleiben, statt sofort entfernt zu werden.
- **Spätestens 2.16:** Legacy Open Terminal (bespoke Codepfad + eigenständige OpenAPI-Tool-Server-Registrierung) vollständig entfernt. Kein dauerhaftes zweites Tool-System als Zielzustand.

### 6.6 Live-Validation-Lauf (2026-09-05)

**Pre-Snapshot:** Open WebUI/Open Terminal/LM Studio alle erreichbar (200), 5 Profile, `tool_server.connections` leer, `terminal_server.connections` 1 Eintrag, keine mcp-runtime-Prozesse, Ports 8010/8011/8021 frei, kein `state/mcp-runtime`.

**Gefundener Fehler (Prozess-Lifecycle, real reproduziert, nicht nur theoretisch):** Der interne Cleanup-Check meldete fälschlich "kein verwaister Prozess", obwohl Port 8021 nach dem Lauf weiterhin belegt war. Ursache: `Start-KIMcpRuntime` trackte `$process.Id` — die PID des unmittelbaren `uv run --with ... python <script>`-Launchers. Live verifiziert: gespeicherte PID (15040) ≠ tatsächlich port-lauschende PID (14424), beide gleichzeitig real und unterschiedlich. Anders als bei Open Terminals `uv tool run open-terminal run` (stabile Top-Level-PID) reparented sich diese Aufrufform in einen neuen, langlebigen Blattprozess. `Test-KIMcpRuntimeProcessIdentity`s CommandLine-Prüfung selbst war korrekt (die echte PID hätte den Check bestanden) — nur die falsche PID wurde je geprüft.

**Fix (minimal, nur `Start-KIMcpRuntime`):** nach erfolgreichem Health-Check die tatsächlich portbesitzende PID via `Get-NetTCPConnection` auflösen, erneut identitätsprüfen (keine bloße PID-Vertrauenslogik — dieselbe CommandLine-Verifikation wird auf die neu aufgelöste PID angewendet), und diese statt `$process.Id` in die PID-Datei schreiben. Live erneut verifiziert: gespeicherte PID = port-lauschende PID, `Stop-KIMcpRuntime` beendet danach nachweislich den echten Prozess (Port wird frei).

**Vollständiger Validation-Lauf nach Fix wiederholt:** erneut alle 13 Punkte grün, Cleanup-Check diesmal auch real verifiziert korrekt (Port frei, PID-Datei leer, `tool_server.connections` wieder 0).

**Registration-Idempotenz explizit geprüft** (mit einem echten, absichtlich angelegten Fremdeintrag `some-other-integration`, um "fremde Einträge bleiben unangetastet" nicht nur zu behaupten, sondern zu beweisen):
- Register auf leerem Zustand → `Registered`, Fremdeintrag unverändert vorhanden.
- Erneutes Register (identisch) → `Unchanged`, kein Duplikat (weiterhin genau 2 Einträge: Fremd + eigener).
- Unregister → `Unregistered`, **nur** der eigene Eintrag entfernt, Fremdeintrag unverändert vorhanden.
- Erneutes Register nach Entfernen → `Registered`, Eintrag korrekt wiederhergestellt (Repair-Semantik für die Open-WebUI-Registrierungsfacette).

**Lifecycle-Idempotenz explizit geprüft:**

### 6.9.3 Complete-Installer-Abhängigkeit (Schritt 5) — kann `open-terminal` entfernt werden?

**Nein, nicht ohne weitere Vorarbeit.** Konkret:

- **Bestehende Installertransaktionen:** `New-KICompletePlan` iteriert `Contracts/COMPONENTS.json` — ein Ziel ohne laufende/pausierte Transaktion wäre von einer Entfernung unberührt. Eine **pausierte** Transaktion (`resume.json`) aus einer älteren Version, die einen `open-terminal`-Schritt referenziert, träfe beim Resume/Replay auf keinen passenden `elseif`-Zweig mehr — der Schrittloop ist eine reine `if/elseif`-Kette ohne generischen "unbekannter Schritt"-Fehlerpfad; das Verhalten wäre unbestimmt (stiller Fall-Through statt sauberem Fehler).
- **Altinstallationen unreparierbar:** Ja. Ohne den `open-terminal`-Eintrag in `COMPONENTS.json` generiert `New-KICompletePlan` für dieses Ziel schlicht keinen Schritt mehr — eine bereits installierte, ggf. defekte Open-Terminal-Instanz wird für den Installer unsichtbar und kann über ihn nie wieder repariert werden (Dateien blieben liegen, unverwaltet).
- **Upgrade von älteren Versionen:** Ja, aus demselben Grund — ein 2.14.x-Ziel, das auf eine Version ohne `open-terminal`-Eintrag hebt, verliert die Repair-/Upgrade-Fähigkeit für seine bereits vorhandene Installation. `Invoke-KICompleteOpenTerminalLifecycle`s Start/Stop-Kette bliebe davon unberührt (sie prüft nur `Test-Path` auf die Starter-/Stopper-Dateien, nicht die Registry), sodass Start/Stop weiterhin funktionieren würde — nur Install/Upgrade/Repair/Validate nicht mehr.

**Fazit:** Eine sofortige Entfernung würde bestehende Installationen in einen unverwalteten Zustand versetzen, ohne dass der Installer das je bemerkt oder meldet.

| | Variante A — Hard Cutover | Variante B — ein Migrationsrelease | Variante C — dauerhaft parallel |

### 6.9.7 Migrationsreihenfolge (Schritt 9, aus den Repo-Befunden abgeleitet)

1. `mcp-runtime` vollständig in den **primären** Complete-Installer-Schrittloop integrieren (heute fehlt das — siehe zentraler Fund oben; ohne das bleibt ein frischer Install nie MCP-fähig).
2. `mcp-runtime` dauerhaft installieren (Lifecycle bereits bewiesen, Phase 1/2).
3. MCP bei Open WebUI registrieren (bereits bewiesen, Phase 2/3).
4. Profile einzeln migrieren, beginnend mit `ki-stack-it-technik` (Parität dort bereits in Phase 3 belegt); Parität nach jedem Profil erneut prüfen.
5. Alle 4 terminal-fähigen Profile migriert; Beobachtungsfenster (Dauer ist eine Produktentscheidung, nicht technisch herleitbar).
6. Automatisierte Deregistrierung von `terminal_server.connections` bauen (existiert heute nicht) und ausführen.
7. Open Terminal deaktivieren (stoppen, **nicht** deinstallieren) — Beobachtungs-/Rollback-Fenster.
8. Nach Ablauf des Fensters: Open Terminal deinstallieren (Dateien/State entfernen).
9. Installer-Altlasten entfernen (`COMPONENTS.json`/`REQUIRED-PAYLOADS.json`/`PAYLOADS.json`-Einträge, Schrittloop-Zweig, Test-Skripte, Payload-Archiv-Generierung).
10. Legacy-Dokumentation bereinigen (technische Doku aktualisieren; Release-Notes bleiben historisch unverändert).

### 6.9.8 Rollback-Strategie (Schritt 10)

- **Open Terminal reaktivieren:** `modules/open-terminal/Start-KIStack-OpenTerminal.cmd` erneut ausführen, solange die Dateien noch vorhanden sind; nach einer Deinstallation `Invoke-KIStackOpenTerminal.ps1 -Action Install` erneut ausführen (Payload muss dafür noch existieren, siehe Schritt 9).
- **Profile zurückstellen:** das in Phase 3 bewiesene Read-Modify-Write-Verfahren rückwärts anwenden (`toolIds` leeren, `terminal:true` wieder setzen) — funktioniert nur, wenn die ursprüngliche Profilkonfiguration vor jeder Migration gesichert wurde (exakt die in Phase 3 etablierte Vorher/Nachher-Praxis).
- **`terminal_server.connections` wiederherstellen:** erfordert die gesicherte Originalkonfiguration (Key, URL) — ohne Sicherung nicht rekonstruierbar.
- **Minimal nötig für Rückfallfähigkeit:** `tools/open-terminal/current/` (Code), der `COMPONENTS.json`/`REQUIRED-PAYLOADS.json`-Eintrag (für Repair/Reinstall über den Installer), und gesicherte Vorher-Snapshots jeder migrierten Profilkonfiguration.
- **Wie lange:** mindestens bis zum Ende des in Schritt 9.7 der Migrationsreihenfolge vorgesehenen Beobachtungsfensters. Ein konkretes Datum ist eine Produktentscheidung des Nutzers, keine technische Ableitung — technisch gilt: solange Open Terminal nicht deinstalliert ist (Reihenfolge-Schritt 8), ist Rollback trivial; danach aufwändiger (Payload-Reinstall), aber möglich, solange die Installer-Artefakte (Reihenfolge-Schritt 9) noch nicht entfernt sind.

### 6.9.9 Empfehlung (Schritt 11)

**Option 2 — Soft Cutover in 2.15: MCP wird Standard, Open Terminal bleibt für einen Release als Legacy-/Rollback-Komponente.**

Begründung: Option 1 (Hard Cutover) würde nach 6.9.3 bestehende Installationen unreparierbar machen und Upgrades brechen — technisch nicht vertretbar, solange `mcp-runtime` nicht einmal primär installierbar ist (6.9-Fund). ### 6.10 Primäre Complete-Installer-Integration von mcp-runtime (2026-09-05)

**Ziel:** den in Phase 4 gefundenen Zustand beseitigen ("Fresh Install → Open Terminal vorhanden, mcp-runtime nicht automatisch vorhanden"), indem `mcp-runtime` in den **primären**, monolithischen `Invoke-KIStackCompleteInstaller`-Ablauf integriert wird — nicht nur, wie bisher, in den sekundären Isolated-Update-Dispatcher.

**Code-Änderungen (`tools/complete-installer/current/CompleteInstaller.psm1`, `Lifecycle/Get-KIStackStatus.ps1`):**

- `Test-KICompleteMcpRuntimeCompliant`: mirrort `Test-KICompleteOpenTerminalCompliant` exakt (Marker-Version, Starter/Stopper/Workspace/Credential-Präsenz) — bewusst inline dupliziert statt eines Cross-Package-Imports von `McpRuntime.psm1`, aus demselben Grund wie bei Open Terminal (im gepackten Release liegt der Modulcode innerhalb von `Payload/McpRuntime/*.zip`, nicht als Sibling-Datei).
- Verdrahtet in `New-KICompletePlan`s Compliance-Berechnung und in die Resume-Recheck-Logik (identisches Muster wie `open-terminal`).
- Neuer `elseif ($step.id -eq 'mcp-runtime')`-Zweig im primären Haupt-Step-Loop, direkt nach `open-terminal`s eigenem Zweig platziert (Step-Reihenfolge: `mcp-runtime` bleibt Order 170, nach `open-terminal` Order 160 — keine künstliche Abhängigkeit gesetzt, wie gefordert; die Reihenfolge ist reine Sequenzierung, keine `requires`-Beziehung). Identische Expand-Payload → Entry-Point-Install/Upgrade/Repair-via-`plannedMode` → Validate → Rollback-bei-Fehler-Struktur wie `open-terminal`s eigener Zweig, keine Parallel-Logik.
- `Invoke-KICompleteMcpRuntimeLifecycle` (mirrort `Invoke-KICompleteOpenTerminalLifecycle`) in `Invoke-KICompleteLifecycle`s Start/Stop-Kette ergänzt — betrifft ausschließlich den Serverprozess, **nicht** die Open-WebUI-Registrierung (die bleibt, wie bei Open Terminal, ein separater Schritt).

**Start-/Stop-Semantik (Schritt 6), real begründet statt geraten:** Open Terminals eigener primärer Zweig startet den Serverprozess **nicht** als Teil von Install (`Invoke-KIStackOpenTerminal.ps1 -Action Install` provisioniert nur Dateien/Credential; der Prozess startet erst über die separate Start/Stop-Kette). `mcp-runtime` spiegelt das exakt: installiert, konfiguriert, MCP-Connection über `Register` vorbereitbar — aber deterministisch startbar über dieselbe Start-KIStack.cmd-Kette wie Open Terminal, nicht dauerhaft automatisch gestartet. Ebenso bleibt die Open-WebUI-Registrierung ein separater Schritt (Open Terminals eigene OpenAPI-Registrierung ist laut Release-Notes 2.14.0 selbst "still requires ONE MANUAL, one-time registration... not yet automated") — keine künstliche Abhängigkeit auf eine bereits gebootstrappte Open-WebUI-Admin-Credential während Install.

**Zentraler, empirisch bestätigter Befund (Schritt 7B/7C):** Bei der Suche nach einem sauberen Seeded-Scratch-Target zeigte sich, dass `cutover-runtime` (Order 70, vor `open-terminal`/`mcp-runtime` bei 160/170) **strukturell nie compliant wird**, sobald sein Pin über den in `Get-KICompleteInstalledVersion`s eingefrorener `acceptedVersions`-Map hinterlegten Wert (`1.6.10`) hinausgeht — aktuell `1.6.14`. Diese Map wird laut eigenem Code-Kommentar **bewusst nie mitgezogen** (ein früherer Versuch dazu führte real zu einem stillschweigend übersprungenen Reconciliation-Bug). Empirisch **gegen die echte Produktion** verifiziert (rein lesendes `-Mode Audit`, 2026-09-05):

| Komponente | installedVersion (Probe) | erwartete Version | compliant |
|---|---|---|---|
| foundation-runtime | 1.0.9 | 1.0.9 | true |

## 8. Sicherheitsumfang für 2.15

2.15 erschließt **keine neue Host-Rechteklasse** — MCP ersetzt ausschließlich, was Open Terminal heute bereits darf. Das volle READ/CONTROL/PRIVILEGED-Modell mit Audit-Log und Kill-Switch ist Gegenstand von 2.16, nicht von 2.15. Für 2.15 gilt: bestehendes `tool_approval_mode`-Verhalten wird unverändert übernommen; Credentials laufen bevorzugt über native Open-WebUI-MCP-Mechanismen (siehe Abschnitt 5), DPAPI nur ergänzend für KI-Stack-eigene Secrets.

## 9. Zusammenfassung

**KI-Stack 2.15 — MCP Foundation & Open-Terminal-Migration**

Einführung von MCP als standardisierte Schnittstelle für lokale Agenten-/Control-Fähigkeiten. Der bestehende Open-Terminal-Dienst wird nicht ersetzt oder geforkt, sondern über seinen nativen MCP-Servermodus direkt an Open WebUI angebunden. 2.15 erweitert dabei bewusst nicht die bisherigen Host-Rechte, sondern migriert ausschließlich vorhandene Terminal-, Datei- und Prozessfähigkeiten auf MCP. Parallel wird die validierte LM-Studio-Concurrency-Baseline übernommen.
