# KI-Stack Complete Installer v2.10.0

Regression- and real-target-validated.

- Complete Installer: 2.10.0 (base: 2.9.0)
- Status: `CentralUpdateChecker_TargetValidated`
- Cutover Runtime: 1.6.13 (base: 1.6.10) -- bumped three times across this release cycle (1.6.11, 1.6.12, 1.6.13); see below.
- Other component versions: unchanged from 2.9.0 (ComfyUI 1.2.4, Visual Models/Workflows 2.0.3, OpenWebUI Agent Pack 1.8.9, OpenWebUI Visual Pack 2.0.5, Codex Local 0.1.4, RAG 0.3.1). ComfyUI's and OpenWebUI's own *contract* changed (reference vs. supported-version model, below) without changing their component/package version numbers, since the payload each ships is unchanged -- only how the Cutover Runtime kernel judges an already-installed, newer version changed, and that lives entirely in the Cutover Runtime package.
- PackageSelfTest: 28/28 passed; repository validation: 34/34 passed

## Scope: central update checker, plus three dependent Cutover Runtime defect corrections

The primary change is a new, central update-checking and safe-update entry point on the Complete Installer's own orchestration layer (`Update-KIStack-All`), plus a small fix to the existing Knowledge-rollback finalization step's validation. That work also required a defect correction inside `KIModuleApplications.psm1`, part of the separately-versioned Cutover Runtime package -- per this repository's own contract (every defect correction requires a new complete package version for the package whose source changed), Cutover Runtime is bumped to 1.6.11 alongside this release.

During real-target validation of this cycle, two further, independent defects were found and corrected in the same Cutover Runtime package, each bumping it again: a v0.28.0-reference-payload overlay could silently downgrade an already-supported, newer ComfyUI installation (1.6.12 partially, with the underlying planner/compliance fix and 1.6.13 closing the last gap -- see the dedicated sections below for the exact sequencing), and the LM-Studio steady-state autostart guard only ran before the server start, not after (1.6.12). Open WebUI had the same "exact reference match" defect as ComfyUI, fixed in 1.6.13. No other component's payload changed in this cycle.

## Planner / Reconciliation: pinned-runtime-reference components can now actually reconcile

`New-KICompletePlan`'s `pinned-runtime-reference`/`recovery-reference` components (Cutover Runtime, Foundation/Runtime, Python/Git, Production Recovery) have no independent, real per-target probe -- `Get-KICompleteInstalledVersion` falls back to a frozen, real-target-validated snapshot (`$acceptedVersions`) for them, so `compliant` there only ever means "matches that static snapshot," never "verified on this target." Previously, if the component-contract pin changed since the last recorded state (`reconciliationNeeded=true`) while that frozen snapshot still happened to match the *new* pin, the planner produced a vacuous `Skip`/`SkippedAlreadyCompliant` instead of routing the change through the existing grouped-kernel dispatch that would actually reconcile it -- a pin bump could silently never take effect on a real target. `New-KICompletePlan` now forces `plannedMode='Upgrade'` in exactly that situation (`compliant AND reconciliationNeeded AND` one of these two reference kinds `AND Mode` is Install/Upgrade/Repair), routing it through the same existing grouped-kernel dispatch (`Invoke-KIStackBuilderKernel.ps1 -Mode Execute`) every other Cutover Runtime upgrade already uses. Ordinary, real-probe-based components (ComfyUI, Integration, and the rest) are completely unaffected -- their existing Skip-when-genuinely-compliant behavior is unchanged. Critically, this fix must never be paired with bumping the frozen `$acceptedVersions` snapshot itself in lockstep with a pin change -- doing so makes `Get-KICompleteInstalledVersion` falsely report "already installed at the new version" without anything real being reconciled, defeating the very fix above; the snapshot only ever moves when a real target has actually been re-validated at a new baseline (the r7 acceptance event), independently of ordinary pin bumps.

## Cutover Runtime 1.6.11: LM-Studio steady-state autostart fix (pre-start)

LM Studio's own Electron shell can (re-)register itself as a competing Windows autostart entry (`HKCU:\...\Run\electron.app.LM Studio`) independently of KI-Stack, including on an ordinary LM Studio start outside any Complete Installer transaction -- previously, only `Install-KICompleteOperations` (run during an Install/Upgrade/Repair transaction) removed this, so compliance could regress silently between installer runs. The narrowly-scoped removal logic (only ever removes an exact, expected `LM Studio.exe --run-as-service` value; anything else throws instead of being silently deleted) is now shared via `Remove-KICompleteLMStudioCompetingAutostart` and also reasserted by the generated `Start-KIStack-LMStudio.cmd` steady-state starter itself, every time, before the server starts.

## Cutover Runtime 1.6.12: LM-Studio steady-state autostart fix (post-start), first ComfyUI overlay-protection layer

Real-target validation of 1.6.11 showed that `lms server start` itself (not just LM Studio's own separate "start at login" GUI preference) re-creates the competing Run-key as a side effect of starting -- the pre-start-only guard from 1.6.11 could not catch a re-creation triggered by the start it was guarding. The same narrowly-scoped, best-effort `Remove-KICompleteLMStudioCompetingAutostart` cleanup is now reasserted a second time, via a shared `:CleanupAutostart` batch subroutine, immediately after the LM-Studio endpoint (`/v1/models`) is confirmed reachable, right before the starter's successful `exit /b 0`. The timeout/error exit paths are unrelated to this steady-state drift and do not run the extra cleanup (regression-verified). No pauschal (blanket) registry deletion is introduced anywhere -- both passes use the exact same value-matching, throw-on-ambiguous contract as before.

Separately, `Test-KICompleteComfyUICompliant` (the Complete Installer's independent, git-aware ComfyUI compliance re-check, introduced earlier this cycle to stop trusting the self-reported `modules/comfyui/installation.json` marker alone) was found, via a real-target incident, to source its CutoverRuntime payload from the target's already-deployed (and possibly stale) `installer/complete` copy instead of the currently-executing package (`-PackageRoot`), and to silently fold a technical probe failure into `compliant=false` -- which, for a real, already-supported, newer ComfyUI installation, incorrectly authorized the Complete Installer's separate, git-unaware `tools/comfyui/current` (`Install-ComfyPayload`) component to overlay the v0.28.0 reference payload onto it (confirmed real-target incident: exactly 160 managed files reset to v0.28.0 content, `.git` untouched, producing the exact reported hybrid state). Fixed: `Test-KICompleteComfyUICompliant` now takes an explicit `-PackageRoot` (matching the sibling `Test-KICompleteModelsWorkflowsCompliant`/`Test-KICompleteVisualPackCompliant` pattern) and fails closed with a clear, thrown error instead of a silent `$false` when the probe itself cannot be evaluated.

## Cutover Runtime 1.6.13: ComfyUI defense-in-depth, Open WebUI reference/supported-version contract

Two further, independent fixes, both completing the "existing supported installation, no automatic downgrade" contract:

- **ComfyUI defense in depth.** The 1.6.12 fix corrected the *planning-time* compliance probe, but nothing yet re-verified support status immediately before the one place that can actually mutate ComfyUI source files. `Invoke-KIStackCompleteInstaller`'s `comfyui` step now re-runs the same real, git-aware `Test-KICompleteComfyUICompliant` check right before `Install`/`Upgrade`/`Repair`; if the target is already a git-managed, supported installation, the mutating `Install-ComfyPayload` call is skipped entirely (`SkippedSupportedInstallation`) regardless of what the plan said. This is defense in depth only -- it does not replace the 1.6.12 `-PackageRoot`/fail-closed fixes, and does not make `tools/comfyui/current`'s payload package itself git-aware (it stays git-free, per its own architectural contract). Verified with a dedicated stale-marker-drift regression that forces `plannedMode='Upgrade'` on a real, clean, supported v0.34.0 checkout and confirms the defense-in-depth layer alone catches it (`HEAD`/working tree unchanged, no `Install-ComfyPayload` backup created).
- **Open WebUI reference/supported-version contract.** `Install-KIModuleApplications`/`Validate-KIModuleApplications` treated `InstalledVersion == ReferenceVersion (0.11.0)` as the only compliant state -- a real-target run found an installed, newer `open-webui 0.11.1` unconditionally reinstalled to `0.11.0` (`pip uninstall open-webui-0.11.1` / `pip install open-webui==0.11.0`) on every Cutover run. New `Get-KIOpenWebUIVersionSupportState`/`ConvertTo-KIOpenWebUISemanticVersion` (same reference/minimum/maximum-supported-version model already established for ComfyUI, not a new framework, no cross-module dependency) now separate `ReferenceMatch` (exact `0.11.0`, still the reproducible Greenfield target) from `Supported` (`>= MinimumSupportedVersion` (`0.11.0`), optionally `<= MaximumSupportedVersion` (currently unbounded)); only a genuinely unsupported state (not installed, below minimum, an unparsable version, or a technically failed version probe) still runs the existing, unchanged pip-install-to-reference path. Verified end-to-end (real Python discovery, real file writes, a recording stub in place of the shared external-process runner instead of a real pip/network call) that an installed `0.11.1` never issues any command matching `open-webui==0.11.0`.

Across both ComfyUI and Open WebUI, the reference version stays the reproducible Greenfield target; a real, already-supported newer installation is preserved; a below-minimum or technically broken installation still goes through the existing, unchanged upgrade/self-heal path (never silently treated as supported); and the existing dirty-repository/health-probe safety nets are unmodified.

## Update-KIStack-All: a central update checker

`Update-KIStack-All.cmd`/`.ps1` (deployed to `C:\KI-Stack`) is a new, single operational entry point that enumerates every KI-Stack-managed component -- every `Contracts/COMPONENTS.json` entry plus OpenWebUI, which is tracked separately via `kernel-config.json` and the managed venv -- and reports, then optionally executes, safe updates.

Each component reports three separate values instead of one: `InstalledVersion` (the real, installed state), `PinnedVersion` (the version KI-Stack currently pins/ships), and `AvailableVersion` (the latest version detected from a real, read-only upstream source, when one reliably exists for that component). A `classification` (`UpToDate`, `PinnedUpdatePending`, `DowngradeRequired`, `Blocked`, `NotManaged`) compares only `InstalledVersion` against `PinnedVersion` and is the sole basis for automatic execution -- KI-Stack remains deterministic and pin-controlled. `upstreamStatus` (`Current`, `UpdateAvailableUpstream`, `Unknown`) is purely informational: an upstream update is never installed unattended, no matter how far `AvailableVersion` is ahead of the pin -- `UpdateAvailableUpstream` is only ever reported. Upstream detection itself reuses real, canonical sources rather than guessing: PyPI's own JSON API for the PyPI-distributed `open-webui` package, and GitHub's own commits API against the Git revision a component's own payload contract already pins (ComfyUI, Integration/SearXNG). Every KI-Stack-authored bundle with no such external upstream project (Visual/Agent/Ballistics Pack, Models/Workflows, Codex Local, RAG, and the rest) correctly reports `AvailableVersion=Unknown` -- a valid, expected state, not a gap.

`-CheckOnly` shows the plan and exits without asking for confirmation or changing anything; `-Component <id[]>` restricts the plan/report to specific component IDs; `-NonInteractive` skips the `EXECUTE` confirmation prompt. OpenWebUI has its own isolated, already real-target-validated update/rollback contract (`Update-KIStack-OpenWebUI.cmd`, 2.8.0) and can be selected and executed entirely on its own. Every other `Contracts/COMPONENTS.json` component instead runs through the existing Complete-Installer-Upgrade batch, which has no per-component isolation -- a real run reconciles every currently non-compliant component in one transaction, reusing that batch's own existing per-step backup/validate/rollback and its stop-on-first-failure behavior; no new single-component installer architecture was built for these components. Because of that, if an explicit `-Component` selection would understate the batch's real scope (naming only some of the components a real run would actually touch), execution is refused before any confirmation prompt or mutation, with a clear error naming the omitted component(s) -- `-Component` never suggests a narrower blast radius than the batch will actually have.

Separately, `Remove-KIStackKnowledgeExperiment.ps1`'s Knowledge-rollback readback validation previously only set a `passed:false` field on its returned object without ever throwing, so a genuine validation failure (leftover Knowledge bindings still present after removal) could be silently recorded by the caller as a successful finalization step. It now throws a clear error on that same condition, matching the sibling Code-Interpreter configuration step's existing throw-on-validation-failure pattern.

Validation: `Test-KIStackUpdateAll.ps1` (14/14) -- all components already at their pin resolves to only `UpToDate`; a single component behind its pin resolves to `PinnedUpdatePending`; an installed version numerically above the pin resolves to `DowngradeRequired`; an explicitly requested but unmanaged component id resolves to `NotManaged` instead of being silently dropped; `UpdateAvailableUpstream` on an already-pin-compliant component is reported on the plan but never triggers execution (checked both in `-CheckOnly` and in a full, non-interactive run); sequential execution runs the OpenWebUI adapter first and then the batch for any remaining component; a failing OpenWebUI adapter stops before the batch ever runs and its rollback detail is surfaced rather than discarded; a non-`EXECUTE` confirmation cancels before anything runs; a partial `-Component` selection against a multi-component batch is blocked before any mutation, naming every affected component instead proceeds normally, and `-Component openwebui` alone is never affected by an unrelated batch ambiguity; no secret handling is introduced anywhere in the new script; and the normal installer's `ReplayComponent`/`Upgrade` dispatch and starter-file registration are unaffected. Full existing regression suite (all prior Complete Installer tests) unaffected.

## Real-target acceptance (Update-KIStack-All, early cycle)

Performed against the existing real target (`C:\KI-Stack`), via a read-only `Update-KIStack-All.ps1 -CheckOnly` run:

- All 14 `Contracts/COMPONENTS.json` components: **`UpToDate`**.
- OpenWebUI: Installed `0.11.1`, Pinned `0.11.0` -> **`DowngradeRequired`**.
- OpenWebUI upstream (real PyPI lookup): Available `0.11.1` -> **`UpdateAvailableUpstream`**.
- **No mutation performed** -- the real drift (OpenWebUI's installed version had moved ahead of the pin since the 2.9.0 cycle) was observed and reported, not corrected, by design; a real, contract-backed downgrade back to the pin remains available on request via the already-validated `Update-KIStack-OpenWebUI.cmd` (2.8.0) but was deliberately not executed in this cycle.

This closes the operational gap of not having a single, central place to check every KI-Stack-managed component's update state, while keeping every automatic action strictly pin-gated. Note `Update-KIStack-All`'s `DowngradeRequired` label above is purely a manual-choice report, produced by comparing `InstalledVersion` against `PinnedVersion`; it is unrelated to the automatic-downgrade defect described below, which lived entirely in the Cutover Runtime kernel's own unattended Install/Upgrade path, not in this reporting tool.

## Known manual follow-up

Unchanged from prior releases: without a supplied OpenWebUI administrator API key, the temporary Knowledge bootstrap-experiment rollback and the Code Interpreter connection configuration remain manual follow-up steps in OpenWebUI after installation (`CredentialRequiredForApiReadback` / `CredentialRequiredForApiConfiguration`).
