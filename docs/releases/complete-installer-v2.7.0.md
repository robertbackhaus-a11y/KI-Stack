Stable release. Published: [GitHub Release 2.7.0](https://github.com/robertbackhaus-a11y/KI-Stack/releases/tag/2.7.0). Fixes a real Codex Local defect reproduced during the 2.5.0 Greenfield acceptance run: LM Studio first-run startup timing.

- Other component versions: unchanged from 2.6.0; see the active-components table in the technical documentation
- Asset: `KI-Stack-Complete-Installer-v2.7.0.zip`, 18,257,207 bytes, SHA256 `438887892bf9cc47ba3bde5432e298b461d24fa4a85117910ac4811a302a81bb`

## Scope: codex-local-module-only

No other installer/build code changed in this cycle. `CompleteInstaller.psm1` and the payload/build pipeline are unmodified beyond informational version literals and the Codex Local component's own compliance-check default. 2.5.0's Greenfield installation, reboot/resume, and RC-build-validation evidence, and 2.6.0's RAG rollback completion, both carry forward unchanged.

## Root cause

`Ensure-KILMStudioEndpointReachable` (in `CodexLocal.psm1`) launched the managed LM Studio starter (`Start-KIStack-LMStudio.cmd`, generated by the Applications component) and then polled the endpoint on its own, independently-timed schedule: 30 attempts * 2s = 60s total, fire-and-forget, with no awareness of the starter process itself. The starter's own legitimate first-run contract can take up to ~120s on a genuine first launch (90s waiting for LM Studio's `lms` CLI to appear after its very first GUI launch, plus 30s waiting for the server it then starts to accept connections). Because the caller's budget was shorter than the starter's own legitimate window, and the starter's exit code was never observed, Codex Local could report the endpoint unreachable and fail while the starter was still legitimately starting. Reproduced live: during the 2.5.0 Greenfield acceptance run, the installer failed with `LM Studio /v1/models ist nicht erreichbar` while LM Studio's first-run GUI setup was still in progress; the run only succeeded after the user completed that setup by hand and resumed.

## Fix

The starter is now treated as the authoritative start/timeout contract rather than a second, independently-timed one:

- The default retry budget (`RetryCount`/`RetryDelaySeconds`) is sized to at least the starter's own up-to-120s window.
- The starter's process handle is tracked (`Start-Process -PassThru`); if it exits with a non-zero code, that failure is surfaced immediately (via a new `starterExitCode` field) instead of being silently outlived by continued polling for the rest of the budget.
- A genuine timeout (the starter never exits and the endpoint never comes up) still fails, unchanged.
- No changes to the LM Studio starter itself (`KIModuleApplications.psm1`) -- no separate defect was found there.

## Validation

`Test-KIStackCodexLocal.ps1` gained a 2.7.0 regression covering exactly this defect, without sleeping anywhere near the real 120s window:

- A static, zero-sleep assertion on the shipped default values (`RetryCount * RetryDelaySeconds >= 120`) -- this alone is the negative control: reverting the fix's defaults fails it immediately.
- Fast behavioral checks that a starter's own non-zero exit code is observed and surfaced without waiting out the full budget, and that a genuine timeout (starter exits 0, endpoint never comes up) still correctly fails.

All 13 checks pass; negative control confirmed (reverting the fix reproduces exactly the expected failures).

Additionally validated against the existing real target (`C:\KI-Stack`, not a fresh Greenfield VM): the real, already-running LM Studio server was stopped via `lms server stop` (GUI left running) so the managed starter was genuinely required, then `Ensure-KILMStudioEndpointReachable` was called directly against the real `C:\KI-Stack` target root and the real starter. The starter was invoked, `/v1/models` became reachable (3 models listed) in ~4.13s, well within the legitimate window -- PASS. Because `lms` was already materialized on this machine from prior sessions, this run exercises the starter's server-start/endpoint-wait phase specifically, not a from-scratch first-ever GUI/CLI-materialization cold start (that sub-path remains covered by the deterministic regression test's static budget assertion only). A real starter failure path was also proven, side-effect-free, using a synthetic starter (`exit /b 1`) under a disposable scratch directory rather than the real production starter: the exit code was surfaced via `starterExitCode` after ~5.12s, well before the configured budget was exhausted.

## Build reproducibility fix (post-merge, no functional change)

After the initial merge to `main`, the resulting build's ZIP differed from the previously validated reference build by 3 bytes. Root cause: `.gitattributes` was missing a line-ending exception for `tools/codex-local/current/**` (the exception already existed for `tools/rag/current/**`, `tools/models-workflows/current/**`, and `tools/complete-installer/current/**`), so `tools/codex-local/current/VERSION` was normalized from LF to CRLF on checkout. Fixed by adding `tools/codex-local/current/** -text` to `.gitattributes` and restoring `VERSION` to its original LF bytes (`0.1.4\n`, 6 bytes, SHA256 `8a3dad16d348c163566a456fcf650d85d7aeeda5e53d01ee1fa8dc15212915a7`). No functional content changed. Two independent rebuilds after the fix reproduced the exact reference hash; the published release asset matches it.
